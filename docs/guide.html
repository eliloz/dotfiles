Working with coding agents: the guide

What exists in ~/dotfiles, what each thing is for, how to drive it, how to set up a computer, how to extend it, and what has been proved.

This page is a map, not a second copy. The READMEs are the source of truth: each part here explains briefly, gives the exact commands and links to the README behind it. Dotted words show their glossary definition when you hover or tap.

Underneath

The one idea

  1. A skill misbehaves. Write down what it should do, as an expectation in expectations.md.
  2. Run it 5 times in the lab. The expectation must fail, or there is nothing to fix.
  3. Change the skill: one change. Run 5 times again.
  4. Keep the change only if that expectation improved and nothing else dropped.

The factory follows the same idea, with the bench in place of the lab: a saved case with a planted defect, run several times before and after a prompt change.

2Daily use: the entry points

What you actually type, in the order you meet it.

A feature, from idea to merged

At the keyboard, one conversation

  1. /grill-with-docs <idea>: answer until nothing is left to ask.
  2. /to-spec: agree the seams.
  3. /to-tickets: agree the breakdown and the blocking edges.
  4. Read the tickets and commit them. In a team's repo, leave them uncommitted: they stay on your Mac.

Unattended, the whole feature

  1. factory run .scratch/<feature>, in its own pane. Every ticket in number order, implement then review, on one branch agent/<feature>. It stops at the first failure.

You again

  1. Read the branch. Decide what it left for you.
  2. Merge it yourself, or delete the branch, fix the tickets and run again.
git add .scratch && git commit -m "<feature>: spec and tickets"     # step 4
factory run .scratch/<feature>                                    # step 5
git log --oneline <your branch>..agent/<feature>                  # step 6
git diff <your branch>...agent/<feature>
git merge agent/<feature>                                          # step 7

One ticket instead: factory run .scratch/<feature>/issues/NN-<slug>.md does the same for that ticket alone, on agent/<feature>-NN-<slug>, from your branch as it is. Merge what blocks it first.

After a failure: run the same factory run again. It skips tickets already done and retries the failed stage. If that stage left commits, it stops and prints the reset command instead, so nothing is dropped without you.

In Claude Code a skill is /name. In Pi it is /skill:name. The full walk-through: factory/README.md, "A typical feature, from idea to merged".

When something goes wrong

What went wrongDo
A skill at the keyboard misbehaved (grill, spec, tickets)/test-skill <name> <the complaint>
A factory run failed (no commit, a Check failing)Read what it printed. A review also writes its log to .sandcastle/logs/. Run the same factory run again once, after the reset it prints if it prints one. If it fails again, the ticket is probably too big or unclear: split or rewrite it.
The implementer or reviewer did the wrong thing, againTurn it into a bench case in the project, then change the prompt in ~/dotfiles/factory/prompts/ (part 6).

Where am I?

  • The tickets: .scratch/<feature>/issues/.
  • The branches: git branch --list 'agent/*'.
  • One record per ticket: .sandcastle/runs/. It names the branch the ticket ran on, agent/<feature> or its own.

Onboarding an existing project

  1. cd into it and run lab doctor. It must be a git repository.
  2. Nothing to install for the skills: every session on this Mac already has them.
  3. Run /setup-matt-pocock-skills. It writes the tracker and glossary sections of AGENTS.md. Choose the local tracker unless the project needs GitHub issues.
  4. Put the project's other facts in AGENTS.md: commands, conventions, where behaviour goes, where the coding standards are. A skill says how to do a job. The project's facts go here, not into a skill or a prompt.
  5. Add .agents/skill-tests/*/reports/ and sidecars/*/reports/ to .gitignore.
  6. For the factory: factory init (factory init --local in a team's repo, so nothing of the factory is committed), then edit .sandcastle/Dockerfile for the toolchain and .sandcastle/factory.json for the setup command and the Checks.
  7. Create .sandcastle/.env with a separate, spend-capped key.
  8. With Docker Desktop running: factory build, factory doctor, factory smoke.
  9. Write no tests up front. The first test in a project comes from the first time a skill misbehaves there.

Read more: agents/README.md, "Onboarding a new project", and factory/README.md, "Setting up a project".

The lab

What it is

An isolated second workspace: a private Herdr window, a copy of the project, a guest Main holding only the thing under test, and a Tester that judges from the screen.

What it's for

Testing a skill or a sidecar from outside, several times in a row, without touching your daily workspace.

How to drive it

CommandWhat it does
lab doctorIs the lab ready?
lab test skill <name> --runs 5 --behindFive runs of one skill against its expectations, with a tally
lab test skill <name> --behind --waitOne trial run
lab report skill <name>The latest report
lab test <Sidecar> --runs 5 --behindThe same for a sidecar
lab test "<steps>" or lab test FILEA scenario: free-form steps, no expectations file
lab stop [ID|all], lab list, lab leftoversClose labs. See what is running or left on disk
lab selftest --behindThe lab's own check. A failure means the lab is broken, not a skill
lab --helpEverything, including the expectations format

Habits

  • Through test-skill. The commands above are for doing a step by hand.
  • From the project's root, always.
  • Commit or git add first. The copy holds tracked files only.
  • --behind, so the lab window opens behind your windows.
  • Five runs, never one. One pass says little.
  • Read Main's transcript in the report, not only the tally. A 5/5 can hide a weakness, and a failure can be a timeout.
  • Never press ctrl+o in a lab's Main pane. It expands the skill's text on screen, where the Tester can read it.
  • Every run spends model tokens. LAB_MODEL sets a cheaper default model.

Where it lives

~/dotfiles/pi/.pi/agent/extensions/lab/, and the shell command ~/dotfiles/scripts/.local/bin/lab.

Status

Proven, and it checks itself

Read more: agents/README.md, "The lab". How a run works: part 4.

The bench

What it is

The lab's counterpart for the factory. It tests a headless stage against saved cases, in Docker instead of Herdr.

What it's for

Knowing whether a change to a factory prompt made the implementer or reviewer better, with numbers.

How to drive it

CommandWhat it does
bench reviewLists the review stage's cases
bench review <case> --runs 3Runs one case three times and tallies each expectation
--stopStops at the first run with a failed expectation
--keepKeeps each run's branch for inspection

Run it from the project that holds the cases. One bench run: it plants a known defect from a patch on a pinned base, runs the stage on that branch, runs the case's Checks with a hidden test, and has a model judge the Expect and Never lines.

The factory

What it is

One command that runs a stage on a ticket in a disposable Docker container: the runner. One copy in dotfiles. Each project keeps only its image, its settings and its key.

What it's for

Implementing and reviewing a feature's tickets, or one ticket, while you are not there. It starts where to-tickets stops and ends at a branch for you to read.

How to drive it

CommandWhat it does
factory init [--local]Writes .sandcastle/Dockerfile, factory.json and .env.example from the templates, and lists what to edit. --local keeps .sandcastle/ out of the repo, for a team's repo
factory buildBuilds the project's image. Again after changing the Dockerfile
factory doctorDocker running, image built, key present, factory.json valid, skills mount found, working tree clean
factory smokeOne "Hello" run: proves the image, the key and that Pi's output is read
factory run <feature>Implements, then reviews, every ticket of .scratch/<feature>/issues/ in number order, on one branch agent/<feature> from the current branch. Skips tickets already done; stops at the first failure
factory run <ticket>Implements, then reviews, one ticket on agent/<feature>-<NN-slug>, from the current branch. Skips a stage already done
factory implement <ticket>One stage: implements one ticket on agent/<feature>-<NN-slug>, from the current branch. Then the Checks, and the record in .sandcastle/runs/
factory review <ticket>One stage: reviews that ticket's branch against the ticket. Fixes what needs no person's decision, commits each fix, then the Checks. Prints what it left for you

Run from the project's root. Not built yet: factory status <feature>.

What the runner sees

  • The ticket's branch, as a git worktree mounted into the container. The rest of your checkout is not mounted.
  • Local files, copied in: an uncommitted .scratch/<feature>/ and an uncommitted AGENTS.md.
  • The global skills, read-only, so Pi in the container loads the same skills as Pi on the Mac.
  • The key in .sandcastle/.env. The agent can read it and the network is open, so use a separate, spend-capped key.

In a team's repo

Nothing of the factory needs committing. factory init --local keeps .sandcastle/ local. Leave .scratch/<feature>/ and, if the repo has none, AGENTS.md uncommitted: a factory run lists them in .git/info/exclude (never committed) and copies them into each runner, so branches hold only the agent's code. Use that file, not your global git ignore: git in the runner cannot see the global one. A partly committed feature folder is refused.

What counts as done

Checked by the factory, not taken from the agent's summary: at least one commit (implement), a clean working tree, every Check passing.

The rules

  • A ticket is committed before a factory run, or wholly local. Local tickets and a local AGENTS.md are copied into each runner.
  • One branch per feature run, one per single-ticket run. Each review sees only its own ticket's commits.
  • The factory never pushes, never opens a pull request and never merges.
  • One model choice for every stage, in src/agent.ts.

Where it lives

~/dotfiles/factory/, and the command ~/dotfiles/scripts/.local/bin/factory. In a project: .sandcastle/.

Status

4How testing works, underneath

For when a result surprises you.

One lab run

Your Herdr
Untouched. The lab never addresses its windows, panes or socket.
The Herdr Lab window
Guest MainPi, started in the project copy, with only the skill under test.
TesterTypes each Do line into Main, reads its screen, takes screenshots, judges.
The project copy
Tracked files only. No .git, no secrets, no .agents/, no expectations or baselines. AGENTS.md only in a skill test.
The report
For each expectation: what was tried, what was expected, what happened, and a quote from the screen.
Teardown
The window, core, terminals and ~/.lab/<id> are removed. Anything left is listed.
  • A second Herdr, never yours. "Herdr Lab" is a copy of Herdr.app with its own bundle id (dev.herdr.lab), core, socket and app home. The copy is cached in ~/.lab/app.
  • Its own Pi profile. A scratch profile that links only your model logins. Lab panes load /split, /sidecar and nothing else of yours.
  • The panes. A skill test has two: guest Main, and the Tester to its right. A sidecar test has three: guest Main, the sidecar that Main opens with /sidecar, and the Tester below.
  • How the Tester drives them. The Tester is a headless Pi started in an empty folder, so it cannot read the project or the text under test. It types with hc send, presses keys with hc keys, reads a pane with hc read and takes a picture with herdr-app shot.
  • Teardown. A test started with /lab in Pi leaves its lab open until /lab stop. So does --keep. lab leftovers shows anything still running or on disk.

Read more: agents/README.md, "How a lab run uses Herdr".

The expectations format

LineMeaningDecided by
Do (Main):What to type, exactly—
Expect (Main):What must happenThe Tester, with a quote
Never (Main):What must not happenThe Tester, with a quote
See (Main): "…"Exact text that must appearThe lab itself
Absent (Main): "…"Exact text that must not appearThe lab itself
Check: <command>A shell command run in the project copy after the step. Exit 0 passesThe lab itself

A ## Before section can hold Run: lines (commands the lab runs first), a Do (Main): line and, in a skill test, a Tools (Main): line. Guest Main gets reading tools only unless that line says otherwise.

One real expectation, from the tests of grilling:

## Opens with one numbered round
Do (Main): /skill:grilling I want a Student to be able to withdraw their own Open Refund Request before a Platform Admin decides it.
Expect (Main): asks several numbered questions in one reply, and gives its own recommended answer under each question
See (Main): "Q1"
Never (Main): edits a file, writes a spec or a plan, or starts building the feature
Never (Main): asks me for a fact it could read in the project, such as where Refund Requests are created or what an Open Refund Request is

The quote rule. Every Expect or Never verdict must quote the screen word for word. A quote that was not on a screen the Tester was shown is rejected. See, Absent and Check lines are decided by the lab and override the Tester.

The whole format: lab --help.

Where tests and baselines live

  • The skill text: once, in dotfiles. ~/dotfiles/agents/.agents/skills/<name>/.
  • The tests: in each project, under .agents/skill-tests/<name>/: expectations.md, BASELINE.md, reports/. A test lives where the problem happened, because its Do lines use that project's domain.
  • BASELINE.md records a hash of SKILL.md, so a skill that moved but did not change keeps its baseline.
  • A project copy shadows the global one. If the project has .agents/skills/<name>/SKILL.md, that is what the lab tests. Use it only to try a change. The report names which copy it tested.
shasum -a 256 SKILL.md | cut -c1-12      # the hash BASELINE.md records

Read more: agents/README.md, "How a skill test finds the skill".

One bench run

The same idea, in Docker instead of Herdr.

  1. A branch is built from the stage's base commit plus the case's change.patch. The bench's own folder is not in it: a stage that can read its test proves nothing.
  2. The stage runs on it. For review, that is factory review on the branch.
  3. The case's Check lines run in the factory image on the result, with the hidden acceptance test copied in.
  4. The Expect and Never lines are judged by a model that sees only the ticket, the change under review and the stage's output. A pass needs a quote that is really in the output.
  5. A report is written to the case's reports/. With --runs N, a tally per expectation.

Settings that belong to one machine

Every config in the repo is used as it is on every machine. What only one machine needs stays out of the repo, in files git ignores:

  • ~/.zshrc.local: shell settings for that machine. .zshrc sources it last.
  • ~/dotfiles/Brewfile.local: that machine's own brew list. Install it with brew bundle --file ~/dotfiles/Brewfile.local.
  • Secrets: in a password manager, never in a file in the repo.
  • Pi's login: ~/.pi/agent/auth.json and settings.json are made on each machine and never tracked.

Read more: README.md, "Shell startup files".

6Extend it

One short recipe each.

A new skill

  • A project skill: write .agents/skills/<name>/SKILL.md in the project. The writing-for-agents skill has the style. Then /test-skill <name> to give it expectations and a baseline.
  • A global skill: add its folder under ~/dotfiles/agents/.agents/skills/, add the links under agents/.claude/skills/<name>/, then run cd ~/dotfiles && stow -R agents. Test it from a project that uses it.

A skill that names one project's code, stack or domain is a project skill.

Read more: agents/README.md, "Adding a skill".

Changing a global skill, and taking Matt's new version

  • Changing one: edit it in dotfiles. Measure it in the project where the complaint came from. Other projects that test the same skill see a stale baseline the next time test-skill runs there.
  • Never keep two copies with the same name. A project copy is only for trying a change. Move the result to dotfiles and delete the copy.
  • Matt's new version: on a branch in dotfiles, put his new SKILL.md in place. In each project with tests for that skill, run /test-skill <name>. Then keep his, keep mine, or merge, with numbers for each.

Read more: agents/README.md, "Changing a global skill".

A sidecar

What it is: a model in its own pane beside Main. It watches your prompts and Main's replies and shows numbered findings. It never edits anything.

How it differs from a skill: a skill does its work inside Main's conversation. A sidecar cannot hold the conversation: it only watches. That is why the flow's skills are not sidecars.

ToDo
Create oneIn Pi: /lab new <Name> [what it does]. Main writes the expectations with you first, then the instructions, then runs the lab until they pass: three tries at most
Use one/sidecar <Name> opens it beside Main. /sidecar send main #N sends finding N to Main as a note. /sidecar stop <Name> closes it
Test onelab test <Name> --runs 5 --behind. lab report <Name> shows the latest report
Change oneAdd the expectation first and see it fail. Then change only ## Instructions, never the expectations, and rerun

A sidecar belongs to one project: sidecars/<name>/sidecar.md. None runs routinely. The Critic in ~/code/sandbox/rentaplace is the only one.

Read more: agents/README.md, "Sidecars".

A widget

Not built. In the mega course a widget is a pane that gathers a status with a script, has a small model judge it, and shows a short list, such as to-dos or issues. Building one would take three things:

  1. A /widget command beside /sidecar, with a widget saved in the project as widgets/<name>/.
  2. A third kind of lab test, beside the sidecar test and the skill test.
  3. A Widget entry in the glossary first.

Build it when a real need shows up, not before.

Read more: agents/README.md, "Widgets".

A bench case for the factory

When: the implementer or reviewer did the wrong thing on real work, again. Not before.

What it needs, in the project, under .sandcastle/bench/<stage>/<case>/:

  • change.patch: the change that reproduces the problem, as a patch from the stage's base commit.
  • expectations.md: Check lines for what can be tested, and an Expect or Never line or two for what must be judged.
  • The stage's stage.json, once per stage: base, spec, hidden test, image, setup, command.

Run every Check on the unreviewed branch before any model runs: it must fail on its defect. Then change the prompt in ~/dotfiles/factory/prompts/, rerun the bench, and keep the change only if nothing dropped.

The lesson that cost the most: a hidden test must check only what the ticket says. Reviewers reshape code. Four times a test pinned more than the ticket did (a field name, a label's wording, its nesting) and failed a correct fix.

Read more: factory/README.md, "Testing the factory: the bench".
